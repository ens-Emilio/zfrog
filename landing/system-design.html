System Design

Um motor de captura que roda inteiro na sua máquina.

O zfrog transforma uma URL em dados de design: screenshot full-page, paleta com papéis, tipografia e CSS computado. Uma CLI fina, um núcleo de orquestração e três engines trocáveis. Nada disso toca um servidor nosso — o produto não tem backend hospedado, por decisão.

Documento de arquitetura, não contrato final. Comportamentos de tongue, pond e da fila descrevem o desenho pretendido e devem ser conferidos contra o README do repositório.

Visão geral

Quatro camadas, cada uma com uma responsabilidade. A CLI não sabe capturar; o núcleo não sabe desenhar terminal; os engines não conhecem a CLI.

CLI jump · tongue · pond · export
Interpreta argumentos, imprime progresso, escreve os arquivos de saída.
Núcleo — orquestração
Resolve o motor, agenda o job, conduz o pipeline e consolida os tokens.
Engines — playwright · scrapy · staticfile + wget
Cada um implementa a mesma interface de captura; o núcleo escolhe por heurística ou por flag.
Armazenamento local — pond/
Screenshots, HTML, tokens e ZIP por referência. Tudo em disco, na sua rede.

Engines

Uma interface, três implementações. Trocar o motor não muda o formato da saída — só como a página é alcançada.

A interface Engine

Toda implementação expõe os mesmos passos. O núcleo programa contra esta interface, nunca contra um engine concreto.

class Engine(Protocol):
    def can_handle(url: str) -> bool: ...
    def capture(url: str, *, viewports: list[int]) -> Capture: ...
    def name() -> str: ...

Auto-detecção

O usuário não precisa escolher o motor. A seleção parte do mais capaz para o mais barato e para assim que encontra um que funciona.

  1. Flag explícita --engine

    Se o usuário declarou o motor, nada é inferido. Exceção: um engine que não pode tratar a URL falha com erro claro, sem cair para outro.

  2. Sonda leve can_handle

    Requisita o documento base e observa sinais: preset de framework JS, tags de app de página única, presença de conteúdo só no bundle.

  3. Decisão

    Conteúdo dependente de JS → playwright. Site estático com muitas páginas → scrapy. Estático e pequeno → staticfile + wget.

  4. Registro

    O motor escolhido e a razão ficam gravados na referência, para o tongue poder relatar depois.

Pipeline de captura

Cinco passos, todos offline. Cada passo produz um artefato que o seguinte consome; qualquer falha é local e não derruba a referência inteira.

  1. 1. Screenshot full-page

    Viewport e altura total da página, nos breakpoints pedidos. Reserva a largura e a altura reais para não cortar nem distorcer.

  2. 2. Extração de tokens

    Varre os elementos, conta ocorrências de cor, tamanho de fonte, família, raio e sombra; atribui papéis (primary, accent, neutro).

  3. 3. Empacotamento em ZIP

    Screenshot, HTML bruto, CSS computado e design-tokens.json vão juntos para um pacote por referência.

  4. 4. Limpeza de trackers

    Remove scripts de telemetria, pings e URLs de rastreio do HTML guardado. O que fica é o documento, não o comportamento de terceiros.

  5. 5. Persistência

    Grava em pond/ sob a chave derivada da URL; atualiza o índice que o pond consulta.

Fila e jobs

Capturas são trabalhos assíncronos. Um worker pega um job, roda o pipeline e publica o resultado. A fila fica em Redis, no mesmo host.

enfileirar

A CLI cria o job com URL, breakpoints e motor resolvido e devolve um identificador.

processar

O worker retira o job, roda o pipeline, reporta progresso por passo.

concluir

Estado final em done ou failed com a causa; o artefato fica em pond/.

  • waitingna fila, aguardando um worker livre
  • runningem processamento, com o passo atual exposto
  • donepipeline completo, artefatos gravados
  • failederro com causa e o passo em que parou

Falha de um job não afeta os outros: o estado vive no job, não no processo. Redis também é o requisito de runtime que mais pesa no setup.

CLI

Quatro verbos. O nome carrega a metáfora do sapo; o comportamento é direto.

jump captura uma URL

Ponto de entrada do produto. Resolve o motor, enfileira e conduz o pipeline até a referência estar salva.

$ zfrog jump http://localhost:3000
referência salva · 165 elementos · 7 cores · 1 família

tongue lê os tokens de uma referência

Relata paleta, tipografia e medidas da referência salva, sem reabrir a página.

$ zfrog tongue localhost
primary #1d1c1a · acento #4f6b3a · JetBrains Mono 16px · raio 2px

pond lista e busca referências

Consulta o índice local: quais referências existem, quando foram capturadas e quanto ocupam.

$ zfrog pond
localhost · 1 referência · 0,4 MB

export escreve tokens para o seu projeto

Converte uma referência em arquivos que entram direto no código: CSS de variáveis ou JSON.

$ zfrog export --css localhost
tokens.css

Artefatos e armazenamento

Tudo o que o motor produz vive em disco. O ZIP é o artefato portátil; o índice torna a coleção consultável.

pond/
  index.json                     # índice: URL, data, motor, tamanho
  localhost/
    capture.zip                  # pacote portátil da referência
    fullpage.png                 # screenshot completo
    page.html                    # HTML limpo de trackers
    computed.css                 # CSS computado
    design-tokens.json           # paleta, fontes, raios, sombras
    tokens.css                   # gerado por export --css
  • design-tokens.jsoncontrato entre captura e export; inclui contagem de elementos e papéis de cor
  • capture.zipunidade de transporte: permite mover uma referência sem perder nada
  • index.jsonfonte do pond; reconstruível a partir das pastas

Runtime

O que precisa existir na máquina. É o custo real de rodar local — e o motivo de não haver versão hospedada.

  • Python 3.12+runtime do núcleo, da CLI e do engine de descoberta
  • Playwright + Chromium≈ 3 GB; necessário para o motor de captura visual
  • Redisfila de jobs e estado de processamento

Captura web consome banda e roda browsers pesados. Por isso o produto não é um serviço: rodando local, os dados ficam na sua rede, e não há superfície de ataque exposta nem custo de infraestrutura.

Deploy do site

Este site é o oposto arquitetural do app: estático puro, hospedado em CDN, sem estado.

  • Páginas estáticas (index.html, este documento e o design system) publicadas no Cloudflare Pages como projeto dedicado, sem build step.
  • Fontes self-hosted e subsetadas; imagens com largura e altura definidas para não deslocar o layout.
  • Sem backend, sem API, sem cookies e sem telemetria — logo, sem banner de consentimento e sem origin na VPS.
  • Não hospedar captura: nenhuma rota do site executa o motor. O site converte, não processa.
